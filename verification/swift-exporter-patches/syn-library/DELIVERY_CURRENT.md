## Supported production selection

There is no verified published coordinate containing this coherent repair. The official versions inspected in `../DELIVERY.md` lack the complete tested fixes; that historical inspection is not a claim about every future release. An isolated artifact path or a fabricated Maven version is not a production solution.

The least custom production route is an official Kotlin release containing the producer and Native header fixes, with matching supported KGP/Native versions. The source patches and regression evidence can support an upstream submission only when that external action is authorized. The released artifacts must then be independently inspected and exercised through final-revision consumer gates. No upstream submission has occurred.

The alternative remains a separately authorized KotlinMania-owned immutable tooling distribution. The earlier proposed repository and coordinate are proposals only. Its minimum closure is:

1. The complete reviewed source patch series and exact upstream revision, including the original error API resource and Native header diff; deterministic archive metadata; all host compiler/bootstrap, source-closure and dependency hashes. Build the unmodified baseline and audit signatures, instruction graphs, full access flags, retained facade references and every intended archive delta. Reproduce the final component twice from clean pinned inputs.
2. A coherent header delivery mechanism. Publishing only an exporter artifact is insufficient. A build setup helper may fetch an official matching Native distribution, verify its complete input manifest, produce a project-local SDK copy with exactly the reviewed header correction, and select it explicitly with the already-tested `kotlin.native.home` property. It must verify unchanged Native binaries and retain the original distribution. This is a proposed production adapter, not an implemented published plugin or permission to change installed SDK files.
3. Explicit tool-only dependency selection through the existing exporter configuration, a locked immutable version/checksum, one exporter provider in the actual worker closure, and no product `commonMain` dependency on host compiler tooling. Library publication must continue to use real published product dependencies. No Maven local, source substitution, official namespace impersonation or overwritten cache artifact is permitted.
4. Versioned dependency/consumer mode configuration with both Werror gates intact. Do not apply a global consumer mode flag to dependency sources by accident. Preserve generated APIs and record the generated test runner separately. Validate all final target gates on suitable hosts, actual Native/Swift consumer tests, and independent publication consumption before any dependent library release.
5. Licensing and provenance artifacts. The experimental archive has no license-named entries, so it is not a release-ready redistribution. Verify upstream and bundled obligations, add required licenses/notices and modified-file attribution, publish source patches/checksums/SBOM/build provenance, and independently verify the final released contents. Reviewed notice additions require a new artifact hash and exact delta audit.

A header patch plus an explicit project-local setup helper avoids redistributing an entire Native SDK or its binaries. It still constitutes adoption of modified compiler inputs and requires the separate production decision; it must never be silently selected in a shared template.

## Exact decision and rollback boundaries

No additional permission is needed for the already-authorized isolated consumer validation. Publication and production adoption remain held. Before implementing the custom delivery route, the required decision is specifically whether to create and release the proposed KotlinMania-owned tooling product plus the coherent project-local Native-header setup mechanism, and explicitly select that published immutable tool only in independently validated consumers. Upstream submission is a separate external action. This variant does not ask to accept the snapshot's removed wrapped API.

If that route is not authorized, the official-release route remains the production path; local diagnostic classpaths do not become an undocumented substitute. No claim is made that an unmodified official release already passes.

A validated rollout must record the prior immutable tool/configuration selection and regenerate coherent outputs when reverting it. Reverting a pin does not turn the known stock failure into success or justify disabling warnings/tests. Installed compilers and shared caches require no rollback because diagnostics do not change them. This plan creates no repository, publication, production configuration or external submission.
